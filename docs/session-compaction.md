# Session compaction 第一版设计

状态：已实现。本文记录已确认方案；第一版具体实现选择见末尾。

## 1. 目标与范围

长对话持续运行或恢复后，会逐渐接近模型上下文窗口。Rudy 在请求模型前压缩历史，让同一 session 可以继续工作。

第一版采用可阅读的文本摘要，不引入后台压缩、长期记忆、向量检索或单独的摘要模型。压缩策略属于 `src/compaction/`，记录和恢复属于 `src/session/`；pi-core 继续负责模型与工具循环，`src/agent.ts` 只负责组装。

核心区分：磁盘上的完整历史不等于本次请求发送的有效上下文。

```text
磁盘：原始消息 + compaction 记录 + 后续原始消息
模型：系统上下文 + 最新摘要 + 保留的近期原文 + 后续消息
```

## 2. 触发与配置

每次对话模型请求前，通过 pi-core 的 `prepareRequest` 钩子检查，包括首次请求、恢复后的请求和工具循环中的后续请求。不是等待某个消息事件，也不由模型主动决定。

```text
预计上下文 tokens >= 有效模型窗口 × 触发比例
→ 先完成压缩，再发送正常请求
```

| 环境变量 | 默认值 | 用途 |
| --- | --- | --- |
| `RUDY_CONTEXT_WINDOW` | 128000（当前配置默认值） | 自定义端点的模型窗口；官方模型应与实际模型元数据及配置语义一致 |
| `RUDY_COMPACTION_THRESHOLD` | 0.8 | 自动压缩触发比例，取值大于 0、小于 1 |
| `RUDY_COMPACTION_KEEP_RECENT_TOKENS` | 20000 | 近期原文的目标保留量 |
| `RUDY_COMPACTION_MAX_TOKENS` | 8192 | 摘要请求的独立初始输出上限 |
| `RUDY_MAX_TOKENS` | 4096（当前配置默认值） | 普通回复的输出设置，与摘要预算独立 |

三个 `RUDY_COMPACTION_*` 变量已接入配置。整数预算必须为正安全整数。

例如窗口为 128000，默认在约 102400 tokens 时触发；切换为 250000 窗口后，触发点为约 200000。80% 是工程默认值，不是模型质量的天然分界。

实际预算还必须为模型输出和请求额外开销留出空间。估算达到 80% 与实际超窗是两件事；估算、端点元数据都可能不准确，不能承诺仅靠比例就绝不超窗。

## 3. Token 计数

优先使用最近一次有效的对话请求 API usage，以它为基准估算之后新增的内容。不是把整个 session 的历次 usage 相加。

不同 provider 的 input、output 和缓存字段由 pi 归一化；实现时核对其含义，避免缓存 tokens 重复计数，也不能盲目把计费总量当作可重放上下文的精确大小。错误、中止、缺失或全零 usage 不能作为可靠基准。

缺少有效基准时，使用本地估算：

```text
estimatedTokens = ceil(ASCII 字符数 / 4 + 非 ASCII 码点数 × 1.5)
```

非 ASCII 按 Unicode 码点计数，而不是 UTF-16 code unit。系统指令、工具定义、用户消息、assistant 内容、工具调用参数及工具结果都需要计入，避免重复计算已包含在 usage 基准中的部分。结构性开销也应留有余量。

压缩、上下文替换或模型变化使旧基准失效后，重新估算有效上下文；单纯恢复且能证明 usage 对应同一模型、同一上下文时可以复用，否则回退估算。摘要生成请求的 usage 只用于记录摘要消耗，不能作为主对话上下文的计数基准。

这是一套启发式估算，不是精确 tokenizer。第一版不新增分词器依赖；相关逻辑封装在 Rudy 自己的模块中，不假设 pi-core 导出了 coding-agent 层的估算函数。

## 4. 摘要输入与输出

摘要模型复用当前对话模型和 provider 配置，使用独立请求，不运行工具循环、不执行工具。摘要调用不经过自身的自动压缩钩子，避免递归。

采用已确认的方案 B：摘要模型看到完整的当前有效上下文，包括旧摘要和近期原文；不重新读取历次已被旧摘要覆盖的全部原始消息。

```text
摘要输入：当前指令上下文 + 旧摘要（如果有）+ 全部当前有效对话
压缩结果：系统上下文 + 新摘要 + 近期原文
```

系统指令和工具定义不依赖摘要保存，恢复有效上下文时单独保留并正确重放。摘要属于历史资料，不得将工具输出或文件中的指令提升为系统权限。

提示词沿用 pi 的默认结构与更新规则，不大改：

1. Goal：目标。
2. Constraints & Preferences：约束与偏好。
3. Progress：已完成、进行中、阻塞。
4. Key Decisions：决策与理由。
5. Next Steps：下一步。
6. Critical Context：继续工作所需的关键资料、文件引用。

实施时从明确版本的 pi 提取原始提示词，注明来源并保留适用的许可证声明；仅适配完整上下文参与摘要、近期原文另行保留的方式，以及篇幅要求。不是复制整个 pi coding-agent。

提示词要求尽量控制在约 2k～4k tokens，但这只是目标。初始最大输出预算为 8192，并受模型支持上限和摘要输入之后剩余窗口约束。不能因为环境变量填了更大数字，就突破服务端限制。

以正常结束、非空文本作为基本成功条件；截断、错误或意外工具调用均不能作为有效摘要提交。第一版不增加第二次模型核查，也不承诺路径、参数等摘要内容完全无误；关键细节允许通过文件工具或历史工具重新核实。

## 5. 近期原文的切分

默认目标保留 20000 tokens，允许最多接近目标的 120%；20% 超额容忍度第一版固定，不另加环境变量。

从最新消息向前，按安全单元累计：普通消息为一个单元；含工具调用的 assistant 消息与该批全部工具结果组成不可拆分单元。一个 assistant 消息含多个 tool call，仍然是一条消息；每个 tool result 是独立消息，但切分时必须保持批次完整。

1. 尚未达到目标时，尝试纳入下一个完整单元。
2. 纳入后不足 `目标 × 1.2`，可以保留；一旦达到目标就停止向前扩展。
3. 纳入后达到或超过 `目标 × 1.2`，不纳入整个单元，并停止扩展；它由摘要承接。
4. 不跳过中间消息再保留更早消息，近期原文始终是连续后缀。

例如目标 20k、边界 24k：

| 已保留 | 下一个完整单元 | 结果 |
| --- | --- | --- |
| 18k | 5k | 保留后为 23k，停止扩展 |
| 18k | 6k | 达到 24k，不纳入，保留 18k |
| 18k | 7k 工具批次 | 不纳入整个批次，保留 18k |

“不纳入”只指不向后续模型请求发送原文。原记录仍在 JSONL，且参与本次摘要；不是从磁盘删除，也不是截断工具结果来凑预算。

如果最新批次本身达到或超过 24k，允许没有近期原文，由摘要承接。此时必须验证生成的消息序列仍满足 provider 的续跑要求，不能出现孤立 tool result；也不能为恢复上下文重新执行旧工具。具体摘要消息表示与续跑方式在实现时用离线测试确认。

压缩后再次检查大小。一次准备过程不循环压缩：超过主动阈值但仍能安全请求时允许继续；仍无法容纳请求与输出时明确报错。后续请求是否再次压缩必须结合有效保留边界和实际缩减情况，防止重复产生无效检查点。

## 6. JSONL 与恢复

原始消息保留，压缩成功后追加独立的 `type: "compaction"` 记录。不覆盖旧消息，不另复制整份备份，也不把摘要伪装成模型实际回复写入原始消息历史。

记录至少表达摘要、时间、保留边界；可记录压缩前后估算量和摘要 usage。具体字段名、消息标识方式和文件版本策略在实现时确定。消息编号必须能稳定映射原始记录，不能因插入 compaction 而漂移。

```text
消息 1～80      被摘要覆盖
消息 81～100    保留原文
compaction     摘要，保留边界指向消息 81
消息 101～110   后续新增

恢复：系统上下文 + 最新摘要 + 消息 81～110
```

系统提示词与工具声明属于运行时配置，不是可重放的历史：恢复（启动/续用）与压缩时，首条 system 消息一律以当前 Rudy 配置重建；磁盘上的 system 记录（基线与 pi 工具变更消息）保留在 JSONL 中，但重建有效上下文时忽略、不回放。

读取最新有效 compaction 后，依据它的边界重建消息，而不是简单读取 compaction 文件行之后的内容。旧 compaction 不作为普通消息重放。没有保留原文时，记录明确的空尾部边界，后续新增消息仍正常恢复。

磁盘的 compaction 类型与 pi-core 消息类型不同。重建时将摘要转为兼容的历史上下文消息，不提升为系统指令。摘要的合成消息不能经普通 `message_end` 订阅再次写成原始对话。

继续支持没有 compaction 的旧 session、缺失尾部换行的修复和已有的中断工具补全机制；完整但非法的记录应报错，不得静默跳过。`list()` 也要识别 compaction，排序仍根据原始对话时间而非仅压缩时间。

写盘封装为一个独立函数：成功返回、失败抛错。严格遵循：

```text
生成并验证摘要 → 检查结果预算 → 追加 compaction 成功 → 替换运行上下文
```

写盘失败不切换内存，不增加复杂恢复机制，也不重新花费模型请求。可能发生部分写入时停止继续追加，要求重新打开或 reset，沿用末尾不完整记录修复。实现时还要验证钩子返回的上下文与 `agent.state.messages`、后续新运行保持一致，不能只缩小本轮请求却让下次 prompt 恢复全部历史。

## 7. 重试与取消

压缩是正常请求的前置步骤，不提供“跳过压缩继续发送”的操作。

| 情况 | 处理 |
| --- | --- |
| 超时、断流、限流、临时服务端错误 | 可取消的退避重试，最多重试两次，共三次尝试 |
| 空摘要或输出截断 | 允许重新生成一次；截断时可在模型与窗口允许范围内将预算提高，例如 8k 到 16k |
| 认证、配置等确定性错误 | 直接抛错 |
| 记录写盘失败 | 直接抛错，不重新生成摘要，不切换上下文 |
| 重试耗尽或压缩后仍无法请求 | 保留原历史，结束本次运行并报告原因；下次继续仍检查压缩 |

8192 是独立初始预算，截断恢复可能临时提高；该配置不是重试全过程的绝对费用上限。临时错误与摘要质量重试必须由统一预算控制，不能嵌套重试无限放大；具体退避时长与总调用上限在实现时明确，并核对 pi/provider 内建重试行为。

交互模式下，忙时第一次 Ctrl+C 取消整个当前运行，包括摘要、退避等待、模型请求与工具执行；停止后再次 Ctrl+C 退出 Rudy。这里的“停止”不是删除 session。取消不提交未完成摘要；已完成落盘的有效检查点不回滚。

signal 是同一次操作的取消通知，应传递给摘要和等待逻辑。手动 `/compact` 不一定让 `agent.state.isStreaming` 为真，因此 CLI 不能只检查这个字段；session 需要覆盖手动压缩的忙状态与取消控制。取消后必须等操作真正结束，才释放互斥。

## 8. 命令与互斥

| 命令 | 行为 |
| --- | --- |
| `/reset` | 创建新 session，恢复系统基线；不继承摘要，旧历史仍保留 |
| `/resume`、`/resume <number>` | 沿用现有选择方式；按最新 compaction 重建目标 session；恢复本身不调用模型 |
| `/compact` | 不要求达到 80%，手动执行同一压缩流程；没有可压缩历史时不生成空检查点 |

这些命令由 Rudy 解析，不作为 steering 或 follow-up 交给模型。

复用 `exclusive()`：prompt、reset、resume、手动 compact 互斥；忙时提示错误，不自动中止，不排队执行。用户需先手动 Ctrl+C，待停止后重新输入命令。现有 CLI 串行读取输入可能缓存运行中输入的行，实现时需确保不会在忙状态解除后悄悄执行这些命令。

自动压缩已经处于 prompt 的互斥区中，调用内部压缩函数，不再次获取同一互斥锁。手动 compact 从互斥入口进入，共用该内部函数。

## 9. 按需读取原始历史

第一版提供分页历史读取工具，不做关键词、空格归一化或语义搜索。模型调用时读取一页，不提前切成多个文件，也不自动回填全部历史。

工具只开放当前 session 的受限历史数据，不接受任意文件路径、目录或其他 session ID。它是 session 数据接口，不是放宽通用文件工具的工作区边界。对该受控入口需专门测试工作区与 session 隔离，不能让模型访问其他工作区的历史。

返回消息角色、稳定编号、原文片段以及继续读取的游标。默认从最近被压缩的历史向前浏览，必要时逐页查回；每页最多 50 条消息，同时限制总返回长度，具体字符预算待实现时确定。

单条超长消息支持按偏移继续读取，返回内容不得超限；工具批次在历史阅读分页中可以跨页，但明确标注角色和关联关系。历史阅读片段不是直接重放给模型的 toolResult 序列，与第 5 节的上下文切分规则不同。

摘要或工具说明应告知模型原历史可以查回、摘要可能有误、读取有开销，避免无目的地遍历整个 session。第一版游标表示、工具名称与消息编号方案待实现时确定。

## 10. 模块建议与验收

实现按 `client -> session -> compaction -> pi-ai` 方向拆分。`src/compaction/` 不依赖 `src/session/`：`tokens.ts` 放置本地估算、保留边界和 usage 基准；`checkpoint.ts` 放置检查点类型与有效上下文投影；`summary.ts` 放置摘要提示词与生成重试；`compact.ts` 放置压缩决策并返回不落盘的结果。`src/session/`：`session.ts` 负责互斥、写盘失败锁存、恢复、接入钩子和对外命令；`store.ts` 负责目录、指针与 JSONL 读写；`records.ts` 负责记录校验；`interrupted.ts` 负责中断工具补全；`history-tool.ts` 实现分页历史读取工具。避免提前设计通用插件框架。

实现必须使用离线模型桩验证，不能调用真实模型 API。重点覆盖：

- 80% 触发、API usage 增量、缺失 usage、中英文估算、压缩后计数失效。
- 首次请求和工具续跑都经过检查，摘要调用不递归触发压缩。
- 20k 目标与 24k 排除边界、工具批次完整性、最新批次过大或空尾部。
- 多次压缩、跨重启恢复、旧 session、保留边界、session 列表与消息事件不重复写盘。
- 空摘要、截断、临时错误、确定性错误、有限重试、写盘失败和部分尾行。
- 手动与自动压缩取消、忙时 slash 命令拒绝、取消完成前不释放互斥。
- 历史分页条数和长度限制、超长单条续读、游标校验、当前 session 与工作区隔离。

代码变更后运行 `npm run check` 和 `npm run test:unit`，不运行真实模型测试。

第一版实现选择：

- JSONL 保持版本 1，新增 compaction 类型；原始 message 记录的一基序号为稳定编号。`firstKept` 指向保留原文，`messageCount + 1` 表示空尾部。
- 摘要转成带历史资料说明的 user 消息，系统状态通过 pi 的 `getCurrentSystemMessage` 独立重建。空尾部以摘要 user 消息继续请求，离线工具续跑测试覆盖此路径。
- `read_session_history` 每页最多 50 条消息、16000 个 UTF-16 字符，游标为 `消息编号:字符偏移:当前session UUID`；游标只能用于当前 session，消息 JSON 片段含原始内容，工具关联另行标注。
- 临时错误按 pi 1.4.0 的分类器判定；250/500ms 退避，provider 的 `maxRetries` 设为 0。所有重试最多合计 3 次，空摘要/截断重试最多一次。
- 普通请求与摘要请求均预留 1024 tokens 的额外开销。每次只压缩一次，并要求估算有缩减、保留边界向前推进，避免无效重复检查点。
- 官方模型使用 pi 元数据上限；自定义端点的输出能力按普通回复和摘要的配置预算中较大者声明，同时受窗口约束。用户需按服务实际能力填写预算。
- 原始提示词取自 pi `v1.4.0` 的上述 compaction.ts，代码标注来源并沿用仓库 MIT 许可证。恢复时不复用旧 usage 基准，避免跨上下文或跨模型误计。
