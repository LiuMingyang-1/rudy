# 今天需要学习的概述

Day 4 解决的问题是：任务不只能在主机上跑，还能派到另一台机器（Worker）上执行，主机照样能看到实时进度、结果和执行所在的设备；网络断了、主机重启了，也不会出现两个 Agent 同时写同一份代码。

核心思路：

1. **Worker 主动连主机，而不是主机连 Worker。** Worker 用一次性配对码换取长期凭据，之后主动发起经过认证的 WebSocket 连接，并上报自己是谁、有哪些仓库、装了哪些 harness。Worker 通常在内网或笔记本上，主动外连更容易穿透网络；主机也不用保存 Worker 的地址。
2. **本机和远程共用同一份执行契约。** 远程 Worker 跑的是和本机一样的 Runner（worktree、会话恢复、证据采集），区别只在“事件怎么送回主机”。这样 Day 2、3 的能力不用为远程再写一遍。
3. **路径和凭证都留在执行端。** 主机只说“仓库别名 X”，Worker 自己解析成本地路径，主机本地路径不会被当成远程路径用。模型 API 凭证只在 Worker 机器上。
4. **可靠投递靠“执行 ID + 事件序号 + 持久化后再确认”。** 主机先把执行 ID 落库再下发；Worker 用执行 ID 识别重复分派。Worker 把事件先写进自己的本地日志，再发给主机；主机按“执行 ID + 序号”去重，写入 SQLite 后才回确认（ack）。断线重连后，Worker 从最后被确认的位置补发。
5. **状态未知时宁可等待，也不分配第二个写入者。** 断线后先显示“正在重连”；超过重连窗口、或者重连后发现事件有缺口、或者 Worker 不再持有这个执行，任务就转为“等待设备”，保留原执行归属。只有确认旧执行已结束，才允许重试或恢复。

# 面试高频追问：难点、边界条件与兜底

### Q1：Worker 怎么配对和认证？凭证泄露了怎么办？

- **配对**：主机生成一个一次性、短时有效的配对码，人工带到 Worker 机器。Worker 用它换一个长期凭据，配对码立即作废。主机只存凭据的哈希，比较用恒定时间比较。
- **撤销**：主机可以撤销设备，撤销后立即断开现有连接，旧凭据再也通不过认证。
- **范围**：只支持一台主机 + 一个 Worker，所以存储上只有一个设备槽位，逻辑简单。
- **传输安全**：协议本身不做 TLS，跨机器时通过 SSH 隧道或 TLS 反向代理暴露主机端口。

### Q2：网络不可靠，怎么保证事件不丢、不重复？

- **不丢**：Worker 产生的每个事件先写进 Worker 本地的小日志并编号，然后发送。主机只有在事件写入自己的 SQLite 之后才回 ack。Worker 只把已 ack 的部分视为安全；断线重连后，从最后一个 ack 之后补发。
- **不重复**：Worker 可能重发已经送达但 ack 丢失的事件。主机按“执行 ID + 序号”去重，同一事件写两次只生效一次。
- **关键点**：ack 的含义是“主机已经持久化”，而不是“主机收到了”。如果主机收到就 ack、写库前崩溃，事件就永久丢了。
- **例子**：Worker 发了事件 5、6、7，主机写完 5、6 后断网，7 的 ack 丢了。重连后 Worker 报告“最后已确认 6，最后产生 7”，补发 7；就算 6 被重发，主机也会忽略。

### Q3：重连时主机怎么判断 Worker 的状态是否可信？

- **Worker 重连时汇报它手上的执行**：每个执行的“最后产生的序号”和“最后被确认的序号”。
- **主机逐个核对**：
  - Worker 根本没提这个执行：说明 Worker 那边丢了或重启了，状态未知，任务转为等待设备。
  - 主机记录的序号落在 Worker 汇报的区间之外：说明中间有补不上的缺口，同样标记并等待，不假装连续。
  - 一致：恢复接收，继续补发。
- **原则**：任何“说不清”的情况都不自动继续，而是明确标出原因，等用户或后续确认。

### Q4：断线多久算“设备离线”？为什么不立即判失败？

- **短暂断线很常见**（Wi-Fi 切换、笔记本合盖），立即判失败会让任务频繁被打断。所以断线后先进入“正在重连”，给一个重连窗口；窗口内回来就无缝继续。
- **超过窗口**：任务转为“等待设备”，但**不结束原执行、不清除归属**，因为 Worker 那边的 Agent 可能仍在运行。
- **心跳**：主机定期 ping，长时间没收到 pong 就主动断开，避免“半开连接”让主机误以为对方还在线。
- **测试**：重连窗口和心跳都用可注入时钟，测试里直接推进时间。

### Q5：怎么保证状态未知时不会分配第二个写入者？迟到事件怎么处理？

- **分派前检查**：只要还有未结束的远程执行，主机就不向 Worker 派新执行；重试或恢复也要求旧执行已确认结束。
- **迟到事件**：每个事件都带执行 ID。旧执行的事件晚到时，只会写到旧执行名下，不会覆盖新执行的状态；主机也只接受当前连接上声明持有的执行的事件。
- **重复分派**：主机先落库执行 ID 再下发，Worker 用执行 ID 去重。主机重启后再次下发同一个执行，Worker 识别出来不会启动第二个 Agent。
- **边界**：这个设计保证的是“不会并发写同一个 worktree”，不保证 Agent 的外部副作用（比如调用了某个接口）严格只执行一次。

### Q6：为什么要区分“已接收”和“已启动”？

- **两个不同的事实**：已接收表示 Worker 记下了这个执行；已启动表示 harness 真的跑起来了。中间可能失败，比如仓库别名找不到、harness 没装、工作区准备失败。
- **价值**：主机能准确判断故障发生在哪一步。只收到“已接收”就断线，说明 Agent 可能还没开始改文件；收到“已启动”后断线，就必须假设 Agent 可能在写，按状态未知处理。

### Q7：远程执行和本机执行怎么复用代码？

- **解法**：把本机 Runner 里“准备 worktree、调 harness、恢复会话、收集证据”抽成两端共用的执行入口。本机直接调用，结果写本地库；远程由 Worker 调用，结果通过事件通道送回主机写库。
- **能力匹配**：用户指定设备，或者主机按“仓库 + harness”能力选择设备。Worker 不具备所需能力，任务就等待，不硬派。
- **合并也在 Worker 上做**：远程修复和审查固定在同一台 Worker，合并在那台机器的仓库里完成，主机只展示远程证据和结果。会话、未提交文件不会自动搬到别的机器。
