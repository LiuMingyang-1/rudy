# 今天需要学习的概述

Day 3 解决的问题是：让 Agent 的改动变成**可隔离、可审查、可安全合并**的代码交付，并支持多个任务的编排：并行、串行（修复 -> 审查）、定时等待和固定间隔的例行任务。

核心思路：

1. **每个写任务一个独立 Git worktree。** 提交任务时把“基线”（比如 main）立刻解析成固定的提交 SHA，从这个 SHA 拉出专属分支和 worktree。这样多个任务可以真正并行，互不踩文件；同一个 worktree 同一时刻只允许一个写入者。恢复和换手复用原 worktree。
2. **证据由 Runner 观测，而不是听 Agent 说。** 任务结束后 Runner 自己把 worktree 里的改动收成一个结果提交，生成相对基线的 diff，记录实际命令的退出码。Agent 的自述（“我修好了、测试通过”）和 Runner 观测到的事实分开存、分开展示。
3. **串行组靠“结果引用”传递。** 审查任务等修复任务成功并且有完整证据后才放行，拿到的是修复的结果提交和 diff。上游失败、取消、或者证据缺失，下游都继续等待，原因写清楚。
4. **审查任务只读。** 审查在执行层就限制写入（Codex 沙箱只读，Claude Code 只给读文件类工具），harness 做不到就启动失败，而不是“提示 Agent 别写”。
5. **定时要防重复，也要防积压。** 例行任务每次触发用“计划 ID + 预定触发时间”唯一标识，登记触发和创建任务在同一个事务里。Host 停机错过多次，只补最近一次；上一轮还没跑完，本次跳过。
6. **合并必须由用户确认具体对象。** 用户确认的是“这个结果提交、合到这个目标分支、目标分支当前在这个提交”。执行前逐项复核，任何一项变了就停，保留所有分支和改动。Rudy 不自动推送。

# 面试高频追问：难点、边界条件与兜底

### Q1：为什么用 git worktree 而不是在同一个目录里切分支，或者每个任务 clone 一份？

- **同目录切分支**：一次只能有一个任务，切分支还会把别人的未提交改动带走或冲突，无法并行。
- **每次 clone**：隔离彻底，但慢、占空间，而且分支在不同仓库里，合并要跨仓库 fetch。
- **worktree**：共享同一个 Git 对象库，创建快；每个任务有独立目录和分支；结果提交直接在原仓库可见，合并就是本地操作。
- **边界**：worktree 目录可能被人替换成符号链接或删除，所以启动前复核它的真实路径、所属仓库和分支是否仍和记录一致，不一致就拒绝启动。

### Q2：“基线”为什么要在提交时就解析成 SHA？

- **坑**：只记 “main”，任务排队期间 main 被人推进了，worktree 拉出来的基线就和用户提交时想的不一样；之后算 diff、判断合并是否安全，都会基于一个漂移的参照物。
- **解法**：提交那一刻就把引用解析成具体提交 SHA 并持久化。之后的 worktree、diff、审查都以这个 SHA 为准，结果可复现。

### Q3：审查任务怎么知道它审的就是修复任务的产物？中间被改了怎么办？

- **坑**：修复任务结束后，它的 worktree 里如果又被人（或残留进程）改了文件，审查看到的就不是当初记录的结果。审查意见和最终合并的代码对不上。
- **解法**：修复结束时 Runner 把改动收成一个确定的结果提交，记下 SHA 和 diff。审查启动前核对 worktree 的 HEAD 仍是这个 SHA 且没有未提交改动，不一致就不启动审查。审查收到的输入是这个提交和 diff，加上 Runner 观测的命令结果，和 Agent 自述分开。
- **合并时再核对一次**：用户确认合并时，要求合并的提交就是审查过的那个，否则提示审查已过期。

### Q4：上游失败了，下游审查怎么处理？为什么不直接也标失败？

- **解法**：下游保持“等待”，原因写成“等待上游任务成功（当前状态：失败/取消/缺少证据）”。用户可以重试上游，成功后下游自动放行；也可以终止剩余任务。
- **为什么不直接失败**：失败是终态，下游一旦标失败，用户重试上游后还得手动把下游再拉起来。等待保留了“上游修好就继续”的可能。
- **证据缺失也算不满足**：上游显示成功但没有结果提交或 diff，同样不放行。审查一个没有产物的任务没有意义。

### Q5：定时任务在 Host 重启后怎么保证不重复创建、不积压？

- **重复**：触发和创建任务如果分两步写，中间崩溃会导致重启后再触发一次。解法是用“计划 ID + 预定触发时间”作为唯一键，登记触发记录和插入任务在同一个事务里，要么都成功要么都没有。重启后再算到同一个触发时间，查到已登记就跳过。
- **积压**：Host 停了一整晚，每 10 分钟一次的例行任务错过了几十次。如果逐个补，重启瞬间涌出几十个任务。解法是只算“当前时间之前最近的那个触发点”，旧的直接放弃。
- **重叠**：上一轮还在跑（或在等待、暂停），本次触发登记为“已跳过”，不建新任务，避免同一例行任务并发。
- **测试**：用可注入的假时钟推进时间，不真实等待。

### Q6：合并前要检查哪些东西？发生冲突怎么办？

- **用户确认的三元组**：结果提交、目标分支、目标分支当前的提交。确认时目标是 A，执行时已经变成 B，说明有人动过，需要用户重新看一眼。
- **执行前检查**：目标仓库当前检出的就是这个分支；没有未提交改动、没有进行中的合并；目标头部没变；先做一次不落盘的合并预演，有冲突就停。
- **停下来时保留现场**：冲突或任何检查失败，都不动结果分支和 worktree，也不留半合并状态，用户可以手动处理。
- **崩溃时的账**：合并做完、还没记账时 Host 崩了，重启后不能凭日志判断，要去看 Git 实际状态再决定。

### Q7：审查任务的“只读”为什么要在执行层做，而不是写在提示里？

- **坑**：提示词是建议不是约束，Agent 可能“顺手修一下”。审查任务改了修复的产物，审查结论就失去意义，还可能和修复任务抢写同一 worktree。
- **解法**：直接用 harness 的权限机制：Codex 把工作区设为只读沙箱，Claude Code 只开放读文件、搜索类工具并关闭外部定制。harness 不支持这些参数时直接启动失败，不降级成“没限制地跑”。
- **原则**：项目指令和 Agent 输出都不能授予新权限，权限只来自 Host 的配置。
