# 今天需要学习的概述

Day 2 解决的问题是：任务中断后怎么接着做，以及同一个任务怎么在 Codex 和 Claude Code 之间换手。

先分清三种“继续”，它们代价和可靠性完全不同：

1. **原生恢复**：用 harness 自己的会话 ID 让它接着上次的对话跑。Agent 拥有完整记忆，效果最好，但只有同一个 harness、同一台机器、同一工作区才能用。
2. **Checkpoint 兜底**：原会话没了（被清理、过期、拒绝恢复），就新开一个会话，把任务简报、最近一次 checkpoint 和当前 Git 状态喂进去。这是**有损**的，Agent 只知道摘要，不知道完整过程。
3. **换手**：Codex 换成 Claude Code。两家会话格式不通，只能像第 2 种那样交接，但 Claude Code 之后有了自己的会话；切回 Codex 时，优先恢复 Codex 自己的原会话，再把“你离开期间 Claude 做了什么”补进去。

几个关键设计：

- **任务 ID 不变，执行 ID 每次新建，会话 ID 按 harness 查找。** 恢复和换手都是“同一任务的新一次执行”。要找会话时，从历史执行里倒序找“同一个 harness 最近一次留下的会话 ID”，所以 Codex -> Claude -> Codex 时第三步能找回第一步的 Codex 会话。
- **Checkpoint 由 Agent 产出，Host 持久化。** 让 Agent 在回复里附一个结构化块：已完成、当前问题、相关文件、验证结果、下一步、推测。“推测”单独一栏，因为交接时最危险的是把 Agent 的猜测当成事实传下去。Agent 自述的进展和 Runner 实际看到的 Git 状态分开给，下一个 Agent 自己核对。
- **只有明确的“会话不存在”才走兜底。** 恢复失败的原因很多（网络、额度、代码报错），只有 harness 明确说“找不到这个会话”才新开会话，其他失败照常判失败。否则一次网络抖动就会悄悄丢掉完整上下文、退化成有损交接。
- **换手前必须确认旧执行已停止。** 这是 Day 1“绝不双写”原则的延续：Codex 还可能在写文件时启动 Claude Code，两个 Agent 会互相覆盖。
- **暂停 ≠ 取消。** 暂停保留会话和工作区，之后可以原生恢复；两者都要等进程真正退出才落状态。

# 面试高频追问：难点、边界条件与兜底

### Q1：原生恢复、checkpoint 兜底、换手，怎么决定走哪条路？

- **坑**：一种做法是统一走“摘要交接”，实现简单，但每次恢复都丢上下文；另一种是只做原生恢复，会话一失效任务就卡死。
- **解法**：分层降级。先找同 harness 的最近会话尝试原生恢复；harness 明确拒绝会话时，降级为“简报 + checkpoint + Git 现状”新开会话；完全没有 checkpoint 时也能继续，但明确告诉用户和 Agent“上下文有限，先检查工作区”。
- **例子**：Codex 跑了一半被暂停，第二天 Codex 本地会话被清理了。恢复时 Codex 报“找不到会话”，系统自动改为新开会话并带上 checkpoint，任务 ID 和工作区不变，用户在事件流里能看到“已降级”的提示。

### Q2：为什么不是“恢复失败就自动新开会话”？

- **坑**：失败原因混在一起。额度用完、网络断、模型报错都会让恢复失败。若一律降级，会把本可以重试原会话的情况变成有损交接，而且用户察觉不到。
- **解法**：只识别“会话不存在”这一类明确信号（匹配 harness 的报错文案，且没有拿到会话开始事件、不是用户主动中断）才降级。其他错误照常失败，让用户决定重试。
- **取舍**：依赖报错文案有脆弱性，CLI 升级改了文案就会识别不到。但识别不到时的结果是“失败、让人处理”，是安全的方向；反过来误判才会悄悄丢上下文。

### Q3：Codex -> Claude Code -> Codex，切回 Codex 时怎么让它知道中间发生了什么？

- **坑**：直接恢复 Codex 原会话，它的记忆停在换手前，会以为文件还是它离开时的样子，可能覆盖 Claude 的修改。
- **解法**：恢复原会话时，检查这个会话之后是否有别的 harness 执行过；有的话，在提示里加上“换手期间的进展”：上次执行的状态和结果、最新 checkpoint、当前 Git 状态。原会话保住完整记忆，增量信息补齐变化。
- **例子**：Codex 写了实现，换 Claude Code 补了测试，再切回 Codex。Codex 恢复后会收到“Claude 新增了测试文件、验证结果如下”，而不是从头再写一遍测试。

### Q4：为什么换手前必须确认旧执行停了？怎么确认？

- **坑**：Host 崩溃后重启，旧 Codex 进程可能还活着在写文件。此时同意用户换成 Claude Code，就是两个 Agent 并发写同一个目录。
- **解法**：任何恢复或换手请求，都要求该任务没有“未结束的执行”。正常停止由进程退出事件确认；Host 崩溃留下的执行，重启时检查当初记录的进程组是否还存活，已退出才结束旧执行、放行恢复，仍存活就保持等待并拒绝。
- **取舍**：宁可拒绝用户操作，也不制造双写。拒绝时把原因直接返回给用户，比如“旧执行尚未确认停止”。

### Q5：Checkpoint 里为什么要把“推测”单独列出？由谁来写？

- **坑**：Agent 很容易把“我觉得测试应该能过”写成“测试通过”。这句话交接给下一个 Agent 后会被当成事实，验证环节就被跳过了。
- **解法**：要求 Agent 在回复里附结构化 checkpoint，字段固定，“验证”一栏只写实际运行过什么、结果如何，“推测”单独一栏。解析失败或字段缺失就忽略这次 checkpoint，不让半成品污染交接。另外 Runner 自己取 Git 状态一并交给下一个 Agent，Agent 自述和客观事实并列，由接手方核对。
- **边界**：Checkpoint 只是进展记录，不快照进程、不回滚文件。进程可能在最后一次 checkpoint 之后又改了文件，所以恢复时总要附上当前 Git 状态。

### Q6：暂停和取消有什么区别？为什么都要等进程退出？

- **区别**：暂停保留会话引用和工作区，之后能原生恢复；取消表示用户放弃这个任务。两者都保留已有改动和日志。
- **为什么等退出**：发出中断信号不代表进程已经停止写文件。只有收到进程退出事件，才把状态写成“已暂停”或“已取消”。否则用户看到“已暂停”就去手动改文件，而 Agent 其实还在写。

### Q7：接入 Claude Code 和 Codex 两种 harness，怎么避免写两套逻辑？

- **解法**：把“启动进程、读 JSON 事件流、超时、进程组终止、判定成功”抽成一份公共流程，每个 harness 只提供三样：启动参数、把它的事件翻译成统一事件（会话开始、消息、完成、失败）、以及“会话不存在”的识别规则。成功判定仍沿用 Day 1 的多条件：拿到会话、拿到完成事件、退出码为 0。
- **权限收口**：两者都用各自的受限模式。Codex 用沙箱限制只写工作区、禁网；Claude Code 关闭命令执行类工具和外部插件，只允许编辑文件。按 spec，执行端提供不了所需限制时，这个角色直接启动失败，不降级运行。
- **恢复时校验会话一致**：恢复时要求 harness 报告的会话 ID 和请求恢复的一致，不一致说明它实际开了新会话，按失败处理，避免以为恢复成功、其实上下文已经丢了。
