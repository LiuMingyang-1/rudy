# 今天需要学习的概述

Day 5 解决的问题是：用户能用一句自然语言交代任务，由 Partner 拆成可执行的任务简报（比如“修复 + 审查”）；长对话不会撑爆上下文；执行端能用上项目自带的指令和 Skills；可选接入长期记忆，但记忆服务挂了不影响任务。最后把前四天的能力串成一个端到端演示。

核心思路：

1. **Partner 只“提议”，Host 才“决定”。** Partner 是一个只读的 LLM Agent：读当前请求、近期对话、滚动摘要和相关任务状态，输出结构化的任务提案（JSON）。真正创建任务的是 Host，它校验工作区、设备、Git 基线等。工作区和设备由用户在命令行指定，不让模型自己选，防止模型把任务指到不该去的目录。
2. **背景信息不能授权。** 之前的对话、任务状态、召回的记忆都只是背景，不能单凭它们创建任务；记忆也不能把任务标为完成或替用户授权。
3. **长对话靠滚动摘要，而且“先存后切”。** 上下文接近上限时生成摘要，**摘要成功落盘之后**才切换到新上下文；摘要失败就保留原记录和旧摘要。输入本身太大、怎么压缩都放不下时，直接提示用户缩短，不无限重试。
4. **执行端用原生能力，不重复造轮子。** Codex 和 Claude Code 自己会加载项目指令（如 AGENTS.md、CLAUDE.md）和 Skills。Rudy 要做的是确认自己加的安全限制没有把这些能力关掉，同时审查任务仍保持只读。
5. **长期记忆是可选增强，不是依赖。** 默认关闭。开启后只保存用户**明确选择**保留的决定，新任务按需召回。服务不可用或认证失败时显示一行状态，任务照常靠本地记录继续；不会自动同步完整会话或仓库内容。

# 面试高频追问：难点、边界条件与兜底

### Q1：为什么 Partner 要设计成只读、只出提案？直接让它调用“创建任务”的工具不行吗？

- **风险**：LLM 的输出受提示词、对话历史、甚至仓库里的文本影响（提示注入）。让它直接创建任务，等于把“在哪个目录、用什么权限执行”交给了一个可被操纵的组件。
- **解法**：Partner 只输出 JSON 提案（目标、范围、完成条件、约束、用哪个 harness、是否审查）。执行位置（工作区、设备、基线）由用户在 CLI 显式给出，Host 统一校验后创建。Partner 自己也没有写文件的能力。
- **好处**：Partner 输出错了，最坏结果是生成一个不合适的简报，用户能看到；不会越权执行。

### Q2：Partner 输出的 JSON 不合法、或者回答到一半被截断怎么办？

- **解法**：只有模型正常结束（不是因为长度上限被截断）且输出能解析成 JSON，才接受提案；否则明确报错“Partner 没有完成提案”或“没有返回 JSON”，不去猜、不修补。
- **为什么不自动重试**：重试会叠加成本，而且同样的输入大概率得到同样的问题。把错误交给用户，比悄悄重试多次更可控。

### Q3：滚动摘要为什么要“先存后切”？摘要失败怎么办？

- **坑**：先切换上下文再写摘要，写失败时内存里的旧对话已经丢了，磁盘上又没有新摘要，等于把对话历史清空了。
- **解法**：摘要生成并成功写盘后，才把它作为新的有效上下文。任一步失败，保留原记录和旧摘要，下次还能继续。
- **保留当前请求原文**：压缩时把本轮用户请求原样保留，不压进摘要，避免模型“记不清用户刚才到底要什么”。

### Q4：输入太长、怎么压缩都放不下时怎么办？

- **坑**：常见实现会循环“压缩 -> 还是放不下 -> 再压缩”，要么死循环，要么把摘要压到没有信息量。
- **解法**：发请求前先估算“系统提示 + 本轮输入 + 预留输出”的大小，单这部分就超过模型窗口时，直接提示用户缩短输入；摘要重试也有上限。
- **取舍**：把问题交还给用户。系统无法替用户决定该删哪部分输入。

### Q5：执行端的项目指令和 Skills 怎么保证生效？和安全限制冲突吗？

- **原则**：Rudy 不自己实现 Skills，交给 harness 原生加载。Rudy 只负责两件事：确认自己加的受限参数没有把这些能力关掉；审查任务保持只读。
- **实际踩到的坑**：Day 5 用本地模型桩实测时发现，某个受限参数会让 Claude Code 漏加载项目指令和 Skills。最后通过它的原生加载机制恢复了加载，同时保留了限制。教训是安全参数会顺带关掉别的能力，要实测，不能只看文档。
- **边界**：Skill 目录里可能有指向工作区外的符号链接，加载器会跟随它读到外部文件。所以对含越界符号链接的插件目录直接跳过，守住“模型可见的文件不出工作区”这条线。

### Q6：长期记忆服务挂了怎么办？为什么记忆不能决定任务状态？

- **降级**：记忆调用有超时，任何失败（服务没起、认证过期、命令不存在）都转成一行状态提示，比如“记忆服务不可用，使用本地上下文”，委派照常进行。测试里用模拟的失败命令验证了这一点。
- **为什么不能决定状态**：记忆是过去的、可能过时的信息，也可能被污染。任务是否完成，由 Host 根据执行证据判断；是否授权，由用户当场决定。记忆最多作为 Partner 生成简报的参考背景。
- **隐私**：只保存用户明确选择的决定，并加专用标签，召回时只搜这个标签。不自动同步整段会话或代码。

### Q7：完整演示要证明什么？怎么讲清“重启、恢复、交接”的区别？

- **演示流程**：Partner 把一个可复现的 bug 拆成“修复 + 审查”；远程 Worker 上的 Codex 在独立 worktree 修复；中途重启主机，任务恢复；同一台 Worker 上的 Claude Code 审查；用户看 diff、验证结果和审查意见后确认合并。另演示一次 Codex -> Claude Code -> Codex 换手。
- **三者的区别**：
  - **重启**：主机进程没了，任务状态从 SQLite 恢复。不确定旧执行是否还活着时进入等待，确认停止后才继续。
  - **恢复**：同一个 harness 用自己的原生会话 ID 接着跑，上下文完整。
  - **交接**：换 harness，或原会话失效，只能靠简报 + checkpoint + Git 现状，是有损的。
- **每次故障都要能说清三件事**：当前任务状态、判断依据（比如“旧进程组仍存活”）、下一步恢复动作。这是整个项目“状态可解释”原则的落点。
